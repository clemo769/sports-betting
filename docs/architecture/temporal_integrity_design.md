# Temporal Integrity Design Review

**Status:** Design only; no source, schema, data, or configuration changes were made.  
**Reviewed:** 2026-11-01  
**Scope:** Point-in-time feature generation and prediction traceability for the existing football pipeline.

## 1. Current-State Findings

The repository currently has several different time concepts, but the code and field names do not consistently preserve them:

- Provider event date/time is represented in parser output as `match_date_utc` and `source_event_ts`.
- Provider/snapshot availability is represented as `source_available_ts` on source rows and feature manifests.
- Collection time is represented as `ingest_ts`.
- The feature builder optionally writes `prediction_cutoff`; the database stores it on `feature_set` and `prediction`.
- Prediction generation is stored as `predicted_at`; `feature_set.created_at` is database insertion time unless supplied explicitly.

There is no source publication timestamp field, no distinct actual-start/completion timestamp, no prediction-mode field, and no feature/model artifact hash in the relational schema. The current implementation does not prove that the values used to build a feature were available at its cutoff.

### FDCO

[`scripts/parse_fdco_csv.py`](../../scripts/parse_fdco_csv.py) reads FDCO `Date`, `HomeTeam`, and `AwayTeam`; it does not use the available `Time` column. `Date` is parsed with `dayfirst=True` into a timezone-naive pandas timestamp. The parser writes the date as `match_date_utc` at midnight and copies the date-only value to `source_event_ts`. The `_utc` suffix is therefore inaccurate for the current output. `source_available_ts` is intentionally null because FDCO does not provide a row-level publication/update time. `ingest_ts` is created with deprecated `datetime.utcnow().isoformat()`, which omits an offset.

### OpenFootball

[`scripts/fetch_openfootball.py`](../../scripts/fetch_openfootball.py) requests the Premier League JSON file and retrieves a GitHub commit timestamp/SHA for the exact file path. It writes the `date` field to date-only `match_date_utc`; the `time` field is copied into a timezone-naive `source_event_ts` string. `source_available_ts` is the GitHub commit timestamp. This proves that the pinned file snapshot existed at that commit, but it does not prove the earliest publication time of each match datum. The current field therefore carries a conservative snapshot evidence time, not a row-level publication timestamp.

### Linking

[`src/linking/match_linker.py`](../../src/linking/match_linker.py) parses `match_date_utc` with pandas, uses its ISO representation in the primary key, and falls back to date-only matching when an exact time is absent. It does not impose a UTC timezone, resolve local zones, or reject mixed timezone inputs. Since both current parsers generate date-only event keys, the real 2023–24 link succeeds at day precision; it cannot establish exact kickoff ordering for same-day matches.

### Feature and prediction time handling

[`src/features/temporal_contract.py`](../../src/features/temporal_contract.py) correctly treats unknown availability as unavailable and rejects comparisons between naive and aware timestamps. [`src/features/feature_builder.py`](../../src/features/feature_builder.py) sorts rows by parsed event time, creates features before applying results from a same-time group, and supports global/per-match cutoff metadata. However:

1. Elo/form inputs are selected using event-time order only; `source_available_ts` is not used by the builder.
2. `_resolve_prediction_cutoffs` rejects a cutoff earlier than the target event (`event_time > cutoff`). That is the opposite of the approved strict pre-match contract, which requires the cutoff to be strictly earlier than scheduled kickoff.
3. The builder does not persist source-record IDs, availability evidence, feature definition/schema versions, or a feature artifact hash alongside the parquet.
4. Feature artifacts default to no cutoff column when no cutoff is passed.

[`scripts/persist_predictions.py`](../../scripts/persist_predictions.py) requires a timezone-aware cutoff and source-record IDs whose database availability is known and no later than the cutoff. It reads feature version from the registered model and assigns that version to the new feature set; the input parquet/manifest does not assert its own feature-definition version, so compatibility is not independently proven.

The database does distinguish `prediction_cutoff` from `predicted_at`. `feature_set.created_at` is generated by the database by default and currently does not necessarily equal the time the parquet artifact was created.

## APPROVED ARCHITECTURAL DECISIONS

- The system has two explicit prediction modes: `STRICT_PRE_MATCH` and `RETROSPECTIVE_RESEARCH`. Persist the mode with every feature artifact and prediction. The modes must never be silently mixed.
- `STRICT_PRE_MATCH` requires all historical inputs to satisfy both event-time and known availability rules. Its exact timing constraints are:

  ```text
  prediction_cutoff < scheduled_event_time
  predicted_at < scheduled_event_time
  prediction_cutoff <= predicted_at
  source_available_time <= prediction_cutoff
  historical_event_time < target scheduled_event_time
  ```

- `RETROSPECTIVE_RESEARCH` may include historical inputs whose availability is unknown, but must be explicitly labelled and must never be presented as strict point-in-time evaluation. Event ordering and append-only correction reconstruction still apply.
- In-play prediction is outside M1. It requires a separate mode, event-state model, and design; it must not be emulated by relaxing `STRICT_PRE_MATCH` inequalities.
- Use IANA timezone identifiers and resolve the actual event venue wherever possible. For the currently supported Premier League sources, the proposed historical default is `Europe/London` for matches at their usual England/Wales venues, resolved through the historical IANA tz database. A known neutral or non-UK venue uses that venue’s own IANA zone instead.
- Preserve raw provider date/time values and timezone evidence. Never fabricate a UTC instant when the venue/zone or precision cannot be resolved.
- Keep provider publication, verified source accessibility, first observation by the collector, snapshot availability, and ingestion as distinct evidence. First-observed time is a conservative upper bound on when the collector could access the item; it is not proof of original provider publication.
- Treat an OpenFootball GitHub commit timestamp as snapshot-level availability evidence only. Preserve the exact commit SHA and source snapshot identity; do not describe the commit as an individual match’s original publication timestamp.
- Require immutable source snapshot identity in strict mode. Require SHA-256 hashes for feature and model artifacts, and preserve training dataset identity and configuration for reproducibility.
- Result observations and source revisions remain append-only. Reconstruct the result state as of the cutoff; later corrections must never rewrite an existing feature artifact or prediction.
- Any M1 database evolution is additive to the six existing tables. Do not add a new table unless a specific integrity requirement is demonstrated and cannot be met by the existing entities.

## 3. Proposed Temporal Contract

Use UTC-aware instants for all resolved canonical timestamps. Preserve each provider’s original text, IANA timezone identifier, venue evidence, and temporal precision rather than relabeling naive local time as UTC. A timestamp with unknown zone or insufficient precision remains unknown at the canonical instant level.

### `STRICT_PRE_MATCH`

This is the only mode that may be described as a point-in-time prediction or backtest. The mode is explicit in the feature manifest and persisted prediction. It requires:

- `prediction_cutoff` and `scheduled_event_time` are valid, timezone-aware instants.
- `prediction_cutoff < scheduled_event_time`.
- `predicted_at < scheduled_event_time`.
- `prediction_cutoff <= predicted_at`.
- Every source-derived historical value has known, defensible system-availability evidence no later than the cutoff.
- Every contributing result is from a completed event strictly earlier than the target event.
- The applicable source snapshot identity is immutable and present.
- Feature and model artifacts pass hash and compatibility checks.

Unknown source availability rejects that input from strict feature history. A strict feature set cannot silently include an unknown-availability row.

### `RETROSPECTIVE_RESEARCH`

This mode supports exploratory historical research when source availability is unknown. Its mode must be stored in the artifact manifest and prediction record, surfaced in reports/APIs, and excluded from strict point-in-time evaluation aggregates. It still requires a fixed source snapshot, deterministic feature algorithm, event-time ordering, and as-of correction state. It may not claim that its inputs were available at the historical cutoff. `predicted_at` records the actual research run time and need not precede the historical scheduled event time.

No implicit default between these modes is allowed. In-play prediction is out of M1 scope and requires a separate future design.

For one prediction target, define:

- `scheduled_event_time`: canonical scheduled kickoff known for the target at the prediction cutoff. Reuse `match.event_time` with this explicit meaning for the initial contract.
- `actual_start_at`: actual start, nullable unless supported by reliable evidence.
- `completed_at`: event completion, nullable unless supported by reliable evidence.
- `source_published_at`: provider-asserted publication time, nullable and distinct from system accessibility.
- `source_available_ts`: earliest defensible time the exact source information was accessible to this system, nullable when unknown.
- `ingest_ts`: when this system actually collected the source record.
- `prediction_cutoff`: latest information time allowed for the feature set and its prediction.
- `predicted_at`: when inference actually ran and emitted the prediction.
- `feature_artifact_created_at`: when the serialized feature artifact was produced; this can map to `feature_set.created_at` if the writer passes it explicitly rather than relying on insert time.

The exact inequalities are mode-dependent. For `STRICT_PRE_MATCH`:

```text
source_available_ts <= prediction_cutoff
prediction_cutoff < scheduled_event_time
predicted_at < scheduled_event_time
prediction_cutoff <= predicted_at
historical_event_time < target scheduled_event_time
completed_at <= prediction_cutoff, when completed_at is known
```

Source-availability equality is allowed. Scheduled kickoff and prediction-generation equality are not allowed in strict mode. Historical event equality is not allowed: events at the same event-time instant are handled as one group and cannot affect each other.

Do not infer UTC from a local date, infer publication from event time, or set source availability equal to ingestion merely because ingestion is known. The five evidence times may have the same value only when their evidence independently supports that equality. `RETROSPECTIVE_RESEARCH` may admit unknown source availability, but must carry the mode designation and a fixed snapshot identity.

## 4. Timestamp Semantics and Source Adapters

| Concept | Meaning | Current representation | Proposed treatment |
| --- | --- | --- | --- |
| Scheduled event time | Scheduled kickoff as known for a fixture | Date-only `match_date_utc`; DB `match.event_time` | Store the scheduled kickoff as an aware UTC instant after venue-based IANA resolution. Preserve original local date/time, venue, zone, and precision. |
| Actual event start | When play actually begins | Not represented separately; `source_event_ts` is provider-specific | Store separately when reliably sourced; never overwrite scheduled kickoff. |
| Event completion | When the event is complete | Goals and `match.status`; no completion instant | Store separately when reliable. A final score alone does not establish exact completion time. |
| Provider publication time | When the original provider says information was published | No dedicated field; FDCO unknown; OpenFootball has commit metadata | Preserve optional provider assertion. It is not system availability by itself. |
| Verified source accessibility time | When the exact information is verified accessible to this system | Current `source_available_ts`, with mixed evidence semantics | Store separately with its evidence basis/reference. Unknown remains null. |
| First observed by collector | First time this collector observed the item | Not currently distinct | Preserve separately. This is a conservative upper bound on when the collector could access the item, not proof of provider publication or earliest possible access. |
| Snapshot availability time | When an immutable snapshot containing the data was available | OpenFootball commit timestamp currently copied into `source_available_ts` | Preserve as snapshot-level evidence with the exact commit SHA/snapshot ID; do not call it per-match publication time. |
| Ingestion time | When this system actually collected the record | `ingest_ts`; FDCO parser currently emits naive `utcnow()` text | Always aware UTC for new writes. It is separate from all provider/accessibility evidence. |
| Prediction cutoff | Information boundary for one feature/prediction | Feature parquet optional column, manifest, DB fields | Required, aware UTC, explicit mode, identical on feature set and prediction. In strict mode it is strictly before kickoff. |
| Prediction generation time | Actual inference time | `predicted_at` | Required aware UTC. In strict mode it is before kickoff and at or after the cutoff. |

### FDCO conversion

FDCO `Date` and `Time` must be parsed together. `Time` is a local wall-clock value, not UTC. Resolve the actual venue to an IANA timezone and convert the combined timestamp to UTC while retaining the original values, venue, zone identifier, and conversion evidence. For the currently supported Premier League sources, propose `Europe/London` using historical IANA tz database rules for ordinary England/Wales venues. Use the actual venue’s zone for neutral or non-UK venues. Daylight-saving ambiguous or nonexistent times must be rejected or quarantined for explicit resolution; they must not be guessed. If a row lacks a usable `Time` or venue resolution, retain date precision as unresolved and do not claim kickoff-level ordering.

FDCO’s source documentation/convention for the meaning of `Time`, match venue resolution, and historical timezone database version still need verification. A league-wide `Europe/London` fallback is appropriate only for the supported Premier League venue set where the venue is known to be in England/Wales; it is not a universal rule for all competitions.

### OpenFootball conversion

OpenFootball’s `date` and `time` must be treated as source-local until the actual venue’s IANA timezone is resolved. For Premier League fixtures, apply the same venue-based `Europe/London` historical policy where the venue is in England/Wales. Preserve raw JSON date/time, venue and timezone evidence, and do not assume the JSON time is UTC. The GitHub commit timestamp is snapshot-level availability evidence only. Preserve the exact commit SHA and source snapshot identity; never describe it as an individual match’s original publication timestamp.

## 5. Availability Evidence and Leakage Rules

Represent these as distinct fields/evidence values:

1. `provider_published_at`: source-asserted publication time, nullable.
2. `verified_accessible_at`: time supported by evidence that this exact information was accessible; this is the strict eligibility time when its basis is accepted.
3. `first_observed_at`: first collector observation. It is a conservative upper bound on when the collector could access the information, not proof of original provider publication.
4. `snapshot_available_at`: time an immutable snapshot containing the information was available. For OpenFootball this is the commit time plus exact SHA/snapshot identity.
5. `ingest_ts`: actual system collection time.

Keep the evidence basis explicit (`provider_publication`, `verified_access`, `first_observed`, or `snapshot`) and retain an evidence reference. Existing `source_available_ts` can represent the effective verified accessibility time after its semantics are made explicit; it must not silently switch between these bases. A snapshot timestamp can show that a pinned snapshot existed by that time, but does not establish an individual row’s original publication time.

Define the actual as-of eligibility function for a historical result record `r` and prediction cutoff `c`:

```text
eligible(r, c) =
  r.match_status == completed
  AND r.historical_event_time < target.scheduled_event_time
  AND r.verified_accessible_at is known
  AND r.verified_accessible_at <= c
  AND r.result_observed_at <= c, when replaying the system's actual recorded state
  AND r.completed_at <= c, when completion time is available and required
  AND r is not disputed as of c
```

The query must be evaluated **as of the cutoff**, not from today’s final result state. A later correction must not rewrite a prior feature set. Resolve corrections by considering only observations and source revisions available by the cutoff; if competing observations remain unresolved, exclude that result or mark the feature set invalid for strict evaluation.

For verified live ingestion, record provider publication, verified accessibility, first observation, snapshot availability, and actual ingestion separately. If an item is first seen by the collector at ingestion, preserve that as `first_observed_at`; it is not provider publication. If the collector’s first observation is used as the conservative strict availability point, record the basis explicitly and permit use only at cutoffs at or after that observation. For retrospective files with no publication/accessibility evidence, `STRICT_PRE_MATCH` must exclude those source-derived results; `RETROSPECTIVE_RESEARCH` may include them only with its explicit mode label and snapshot identity.

Unknown availability is not zero, not always available, and not equal to event or ingestion time. Source availability should be validated both during feature construction and at persistence, so the manifest cannot bless a feature that was already computed from ineligible data.

## 6. Feature-Generation Algorithm

For each target match:

1. Resolve its scheduled kickoff as a timezone-aware UTC instant and require an explicit mode. In `STRICT_PRE_MATCH`, require `prediction_cutoff < scheduled_event_time`, `predicted_at < scheduled_event_time`, and `prediction_cutoff <= predicted_at`.
2. Load an immutable source snapshot and its provenance manifest. Reject duplicate/missing source identities and invalid timestamp zones before computing features.
3. For each candidate historical match, select only result observations known by the cutoff. Require completed status, strict prior event order, and verified accessibility no later than the cutoff. Apply the correction state that existed at that cutoff; never use today’s corrected state to reconstruct a past prediction.
4. Group target and historical events by canonical event instant. Compute each target’s features from history before updating any result from its own event-time group. Same-time events are mutually isolated.
5. Update Elo and form only after an eligible completed-result group. Use stable ordering for records within a group, but do not let that order expose one same-time result to another.
6. Record missing-feature policy and all input evidence. The current model fills missing features with zero; retain nulls in the audit payload and declare the exact model-input transformation in the manifest.
7. Serialize deterministically, calculate the artifact hash, and persist the manifest and feature set. Re-running with the same snapshot, cutoff, feature version, and algorithm must produce the same semantic feature payload and hash policy.

If a result is delayed, it contributes only to strict cutoffs at or after its verified accessibility time. If a result is corrected, create a new source revision/result observation and a new feature artifact for later cutoffs; preserve earlier feature artifacts and predictions unchanged. For a cutoff before the correction became available, replay the prior observation. An unresolved dispute must not be silently resolved by row order or latest-file contents. In `RETROSPECTIVE_RESEARCH`, unknown availability is permitted but must remain visible in the manifest and the output must not be labeled strict.

## 7. Feature Artifact Manifest Specification

Use a sidecar manifest next to each feature artifact. It may be file-level with a `matches` map or one manifest per feature set; the format must be versioned. At minimum:

```json
{
  "manifest_version": "1",
  "prediction_mode": "STRICT_PRE_MATCH",
  "artifact": {
    "created_at": "2026-11-01T10:00:00Z",
    "content_hash": {
      "algorithm": "sha256",
      "value": "<hash-of-exact-artifact-bytes>"
    },
    "feature_schema_version": "feature-schema-v1",
    "feature_definition_version": "feature-definition-v1",
    "feature_generation_version": "<git-commit-or-build-id>",
    "feature_columns": ["home_elo", "away_elo", "home_form_last3", "away_form_last3"],
    "missing_value_policy": "null-in-artifact; zero-at-model-input"
  },
  "matches": {
    "<match-uuid>": {
      "feature_set_id": "<feature-set-uuid>",
      "prediction_mode": "STRICT_PRE_MATCH",
      "scheduled_event_time": "2026-11-02T20:00:00Z",
      "prediction_cutoff": "2026-11-02T19:45:00Z",
      "source_snapshot_id": "<stable-snapshot-id>",
      "source_record_ids": ["<source-record-uuid>"],
      "source_availability_evidence": [
        {
          "source_record_id": "<source-record-uuid>",
          "source_revision": 1,
          "source_published_at": null,
          "verified_accessible_at": "2026-11-02T19:30:00Z",
          "first_observed_at": "2026-11-02T19:30:00Z",
          "snapshot_available_at": null,
          "ingest_ts": "2026-11-02T19:30:00Z",
          "availability_basis": "first_observed",
          "evidence_ref": "<poll-or-snapshot-reference>"
        }
      ],
      "compatible_feature_definition_version": "feature-definition-v1",
      "compatible_feature_schema_version": "feature-schema-v1"
    }
  }
}
```

The hash must cover exact artifact bytes (or a precisely specified canonical serialization), not the input snapshot. Preserve a separate source/input hash when available. Strict mode requires an immutable source snapshot identity and SHA-256 hashes for both the feature and model artifacts. Preserve training dataset identity and training configuration in the registered model metadata. Model compatibility in a feature manifest is a declaration; the prediction writer must verify it against the registered model and the actual columns/dtypes. Do not infer compatibility from the model registry’s version string alone.

### Database versus artifact manifest

- **Already in relational tables:** `feature_set_id`, `match_id`, `prediction_cutoff`, feature definition version (`feature_version`), generation version, schema version, source references, feature payload, and a creation timestamp; source rows carry revision, availability reference/time, and ingestion time; model/prediction rows carry model version and prediction timestamps.
- **Artifact manifest:** prediction mode, exact file hash, feature columns/dtypes, per-match scheduled event/cutoff context, detailed availability evidence/basis, source snapshot identity, missing-value policy, and builder commit/version.
- **Persisted for cross-checking:** store prediction mode with the feature set and prediction; store the feature artifact hash on `feature_set`, and the model artifact hash plus expected feature schema version on `model`. Existing `source_data_reference.content_hash` denotes an input/source hash and must not be overloaded as the output artifact hash. `feature_set.created_at` may represent artifact creation only if the writer passes the manifest timestamp explicitly.

## 8. Model and Prediction Compatibility

Before inference or prediction insertion:

1. Hash the exact feature artifact bytes and compare with its manifest; reject mismatch.
2. Validate prediction mode and every manifest match ID against the feature rows and persisted `match` records. Reject duplicates, missing/extra rows, invalid event/cutoff timestamps, or unsupported precision. `RETROSPECTIVE_RESEARCH` is never included in strict evaluation.
3. Validate feature definition version, feature schema version, ordered input columns/dtypes, missing-value policy, and model expected input contract. Require definition version to equal `model.feature_version`; require schema version and columns to match the model’s registered training contract.
4. Hash the exact model artifact and compare with its registered model hash before loading. Validate model identity/version and XGBoost best iteration/configuration.
5. Validate every source record/revision and each distinct availability evidence value against the cutoff. Unknown verified accessibility fails strict mode; provider publication, event time, first observation, snapshot time, and ingestion are not interchangeable fallbacks.
6. For `STRICT_PRE_MATCH`, require `prediction_cutoff < scheduled_event_time`, `predicted_at < scheduled_event_time`, and `prediction_cutoff <= predicted_at`. `RETROSPECTIVE_RESEARCH` is explicitly marked and may be generated after the historical event.
7. Persist the feature set and prediction atomically, recording the same feature-set ID, model ID/version, feature version, schema version, cutoff, prediction time, probability map, decision threshold, and hash references.

Current code already enforces several useful parts in [`src/db/ingestion.py`](../../src/db/ingestion.py): aware cutoffs, source availability, feature/model definition-version agreement, same-match references, immutable application-layer IDs, and one transaction for a prediction batch. It does not validate prediction mode, strict pre-kickoff inequalities, feature artifact hashes, feature schema against model, model artifact hashes, or feature versions asserted by the artifact itself. These are new requirements.

## 9. Database Impact

The existing six tables are sufficient for the central relationships; **no new table is required for M1**. The current schema already stores cutoff, prediction generation time, effective source availability, feature/model identities, and correction chain. Additive changes to existing tables are recommended because the full approved contract needs separately queryable evidence and compatibility checks:

1. `source_record.source_published_ts TIMESTAMPTZ NULL`: provider-asserted publication time, distinct from existing `source_available_ts` (effective verified accessibility) and `ingest_ts` (actual collection).
2. `source_record.first_observed_at TIMESTAMPTZ NULL`, `snapshot_available_at TIMESTAMPTZ NULL`, and `availability_basis TEXT NULL`: retain the distinct evidence timestamps and why `source_available_ts` is considered valid. `source_available_ref` remains the pointer to the evidence.
3. `match.actual_start_at TIMESTAMPTZ NULL` and `match.completed_at TIMESTAMPTZ NULL`: preserve actual start/completion separately from `match.event_time`, which should mean scheduled kickoff. Only populate when the source can establish them.
4. `feature_set.prediction_mode TEXT`, `feature_set.artifact_content_hash TEXT`, and optionally `feature_set.scheduled_event_time_at_cutoff TIMESTAMPTZ`: persist mode and exact artifact identity; snapshot the target schedule if it can change after the feature set was generated. Pass artifact creation time explicitly into existing `created_at`.
5. `model.feature_schema_version TEXT` and `model.artifact_content_hash TEXT`: persist the model’s expected input schema and exact model bytes hash. Keep training dataset identity and training configuration in the existing `training_data_reference`/`configuration_reference` JSONB under a validated, versioned contract.
6. `prediction.prediction_mode TEXT`: persist whether the output is strict or retrospective so downstream API/reporting cannot mislabel it. It must agree with the feature set’s mode.

These are additive columns on existing tables; no new entity or migration is implemented by this design. Exact nullability, controlled values, and whether artifact hashes/mode are typed columns versus validated JSON remain human approval items. Historical rows with unknown timestamps must remain null and be excluded from strict point-in-time eligibility; do not backfill fabricated UTC values.

## 10. Test Strategy

### Unit tests

- Parse FDCO date+time using approved IANA zones; test daylight-saving ambiguous/nonexistent local times, missing time, invalid date, and raw-value preservation.
- Resolve Premier League venues with historical `Europe/London` rules and test an actual venue-zone override; verify timezone evidence and raw OpenFootball/FDCO date/time preservation.
- Parse OpenFootball date/time without assuming UTC; verify exact commit SHA/snapshot identity and that the commit timestamp is not treated as original row publication time.
- Test all six timestamp meanings independently and reject naive canonical instants.
- Test source publication, verified accessibility, first observed, snapshot availability, and ingestion independently; verify first-observed is only an upper bound and never publication time.
- Test inclusive `source_available_time == prediction_cutoff`, after-cutoff exclusion, unknown availability by mode, and no ingestion/publication substitution.
- Test strict inequalities `prediction_cutoff < scheduled_event_time`, `predicted_at < scheduled_event_time`, `prediction_cutoff <= predicted_at`; test retrospective labeling and exclusion from strict metrics. In-play is not an M1 test mode.
- Test completed-result gating, strict prior-event ordering, same-time group isolation, deterministic tie behavior, delayed results, and corrected observation replay.
- Test mandatory strict snapshot identity; feature artifact hash, model artifact hash, feature definition/schema/column/missing-policy compatibility failures.

### Integration tests

Use an isolated PostgreSQL test database/schema with migrations applied. Persist match/source revision/observation/feature/model/prediction in one transaction. Verify FKs, same-match provenance, idempotent retry, rollback on any invalid manifest, and source correction immutability. Do not point integration tests at the developer or production database.

### Required historical-delay regression

Create a completed historical match whose provider publication and verified accessibility are unknown or occur after `T_cutoff`, with first observation at `T_first_seen > T_cutoff`, and a later target match with cutoff `T_cutoff`. Build the target feature set twice: once with the delayed result present in today’s source archive and once without it. In `STRICT_PRE_MATCH`, the target feature values must be identical and exclude that result. A second run with cutoff at or after verified availability may include it. In `RETROSPECTIVE_RESEARCH`, the result may be included only with explicit mode and unknown-availability evidence. Assert the manifest explains both outcomes.

### End-to-end test

With synthetic fixtures and pinned local model artifacts: parse -> link -> build an as-of feature artifact/manifest -> train/register or load a registered model -> infer -> persist -> query via read-only API -> attach a later result observation -> evaluate with cutoff-aware result state. Run entirely in isolated temp storage/database. It must not depend on network scraping or production data.

## 11. Migration and Implementation Sequence

1. **Implement the approved mode contract in design/tests first:** strict inequalities, explicit mode persistence, and retrospective exclusion from strict metrics. Keep in-play out of scope.
2. **Approve operational timezone/evidence mappings:** venue-based IANA rules, Premier League `Europe/London` historical treatment, DST ambiguity behavior, and acceptable accessibility evidence.
3. **Correct source adapters:** preserve FDCO Date+Time and OpenFootball date/time, venue and timezone evidence; emit aware canonical instants only when defensible; otherwise retain unresolved precision and availability.
4. **Implement and test the as-of selector:** completed event + strict prior event + verified accessibility by cutoff + correction state as of cutoff. Keep retrospective-only mode explicitly segregated.
5. **Version the feature artifact:** emit a required strict snapshot identity, manifest, feature/model SHA-256 hashes, training dataset identity/configuration, feature version/schema/columns/missing policy. Prediction persistence verifies rather than supplies these claims.
6. **Add the approved additive migration to existing tables only:** publication/access evidence, actual start/completion, prediction mode, schema compatibility and hashes as agreed. Apply only with backup/rollback procedures for any non-empty environment. The audited local DB is empty, but do not assume another environment is.
7. **Wire application validation** and add isolated integration/end-to-end tests before historical backfill or production prediction writes.
8. **Only after temporal correctness:** design evaluation/backtest persistence and calibration comparisons as a separate milestone.

No migration or implementation change was made during this design review.

## DECISIONS REQUIRING HUMAN APPROVAL

The following operational details remain open even though the architectural principles above are approved:

- The verified source timezone meaning of FDCO `Time`, venue resolution source, historical timezone database/version, and handling of fixtures with no reliable venue.
- DST ambiguous/nonexistent local-time policy and whether unresolved date-only rows are excluded from strict mode or admitted only to retrospective research.
- Which provider evidence qualifies as `verified_accessible_at`; how first-observed bounds and snapshot availability map into the effective strict availability timestamp.
- The exact `availability_basis` controlled vocabulary and evidence-reference format.
- Completion semantics (final whistle, end of extra time, or another official completion point) and how conflicting final results become resolved.
- Exact additive fields/nullability/check constraints for source evidence, event milestones, prediction mode, artifact hashes, and model schema compatibility; the approved principle is to extend existing tables and add no M1 tables without a demonstrated integrity need.
- Backup/restore, permissions, and append-only database hardening before the database becomes a system of record.

The audited database currently has zero domain rows, reducing local migration/backfill risk, but it does not establish that other environments are empty. No reset, destructive migration, data update, or source timestamp fabrication is part of this design.
